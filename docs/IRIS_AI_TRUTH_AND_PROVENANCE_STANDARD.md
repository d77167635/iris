# IRIS AI Truth and Provenance Standard

**Status:** Mandatory engineering and governance rule

## 1. Core rule

IRIS must never treat AI-invented content as system truth.

This prohibition applies to more than financial values. It covers every value that can affect evidence, provenance, governance, execution, certification, lineage, or intelligence.

The following may not be invented, fabricated, substituted, or presented as observed system truth by an AI implementation:

- financial values, balances, transactions, accounts, liabilities, assets, investments, or provider observations;
- intelligence findings, predictions, recommendations, scenarios, outcomes, relationships, causal claims, or other derived facts;
- evidence records, evidence states, evidence hashes, evidence boundaries, or source observations;
- execution identifiers, execution versions, operator identities, capability identities, graph identities, or provenance metadata when those identifiers are not already established by the system;
- certification records, certification states, publication states, validation results, lineage records, or proof records;
- timestamps, hashes, run identities, or other metadata when their value is intended to represent an actual persisted system event rather than a value generated by the system at runtime;
- placeholder, mock, seed, demo, synthetic, or illustrative financial content in production behavior.

## 2. Established identifiers versus invented identifiers

A fixed identifier is legitimate only when its authority is established by an existing IRIS contract, schema, provider contract, source-controlled registry, or other audited system source.

A hardcoded identifier created by an implementation without that authority is an AI-generated artifact and must not be promoted to system truth merely because it is technically convenient.

Version identifiers are provenance. They therefore must describe the actual executable implementation that produced an execution record. They must not be independently hardcoded in multiple layers where they can drift from the implementation they claim to identify.

## 3. Evidence and insufficiency

When required evidence or a required semantic input is absent, IRIS must preserve that absence.

IRIS must fail, block, or report insufficient evidence according to the governing contract. It must never manufacture an empty value, substitute an assumed value, create a proof receipt for an unperformed read, or convert uncertainty into certification.

## 4. Runtime provenance

Execution metadata must be derived from the actual runtime implementation and persisted only after the corresponding event occurs.

Where an implementation has a version constant, downstream orchestration and persistence should consume that single source of truth rather than maintain a separate manually synchronized version string.

## 5. Certification boundary

No execution may become certified because metadata appears plausible. Certification requires the actual persisted execution, validation, evidence, semantic dependency proof, lineage, output, and publication conditions required by the applicable certification gate.

A failed execution remains failed until a new execution genuinely passes the gate. Historical failed records must not be rewritten to manufacture success.

## 6. Current audit finding

The Level 3 runtime currently exposes the executor implementation as `iris-recursive-capability-executor-v13` in `recursiveCapabilityExecutor.ts`, while `irisExecution.ts` independently persists `iris-recursive-capability-executor-v11`. Supabase Level 3 runs currently contain the v11 value and are failing the Outcome semantic dependency requirement.

This is a provenance/version-source-of-truth defect. It is not evidence that financial data was fabricated. It is nevertheless a governance defect because the persisted version does not identify the currently declared executor implementation.

The defect must be corrected by binding persisted executor provenance to the actual executor version source, not by changing historical records or inventing a new certification result.

## 7. Non-negotiable implementation test

Before any AI-generated change is accepted into IRIS, verify:

1. Every new identifier has an identified authoritative source.
2. Every persisted observation traces to an actual source observation.
3. Every derived intelligence value traces through its governed dependency graph.
4. Every proof record represents an actual runtime access or event.
5. Every execution version identifies the implementation that actually ran.
6. Missing evidence remains missing.
7. Failed certification remains failed.
8. No financial or intelligence content is invented to satisfy a contract or make a screen appear complete.

**This standard applies to code, database mutations, execution metadata, lineage, certification, UI materialization, and documentation that defines system behavior.**
