# IRIS User Report Inventory and Recursive Composition

## 1. Authoritative product model

IRIS is **one complete hierarchy intelligence relational ontology financial-life state ecosystem**.

Reports are not a separate side of IRIS. Reports are user-facing presentation/composition artifacts generated from the same hierarchy that contains evidence, financial-life state, relationships, intelligence, scenarios, decisions, consequences, outcomes, explanations, and recursively derived intelligence.

There is no fixed semantic depth ceiling on report composition.

## 2. Report composition

IRIS may use **any governed content in any combination** when creating a report, subject to the actual evidence, authorization, lineage, semantic sufficiency, certification, resource, and runtime boundaries.

A report may contain:

- observed provider evidence;
- canonical financial-life state;
- calculated values;
- statistical structures;
- behavioral structures;
- relational ontology content;
- causal analysis;
- risk intelligence;
- opportunity intelligence;
- forecasts;
- scenarios and counterfactuals;
- decisions and consequences;
- explanations and education;
- outcomes and learning when actually observed;
- existing report content;
- recursively derived intelligence; or
- any mixture of the above.

Content does **not** have to contain intelligence to be valid report content. A report can be primarily observational, primarily explanatory, primarily analytical, or a mixture.

Conversely, intelligence is not restricted to one report. The same intelligence node can participate in many report compositions.

## 3. Report naming

IRIS names each user report from the **most important or most empowering actual piece of content in that report**.

The title-selection process must be deterministic and evidence-governed. It may consider materiality, actionability, opportunity, risk, consequence, decision usefulness, explanatory value, temporal importance, and recursive depth.

The title must never invent:

- a financial amount;
- a financial event;
- a positive or negative result;
- causation;
- certainty;
- an outcome; or
- importance unsupported by the composed content.

If no defensible headline exists, IRIS uses a neutral title derived from the actual content rather than manufacturing a compelling claim.

The description is likewise derived from the actual report composition and must not introduce unsupported financial facts.

## 4. User report inventory

The user-facing surface is called the **IRIS Report Library**.

The backend catalog remains the governed **report catalog**.

The library contains two distinct but related inventories:

### A. Report definitions

Global product definitions describe report products IRIS knows how to produce when their evidence and publication requirements are satisfied.

A definition is not a user report.

A definition is not evidence.

A definition does not prove runtime execution.

### B. User reports

A user report is an actual report composed for that specific user from an exact certified execution boundary.

The user-report inventory stores, at minimum:

- user identity boundary;
- report identity;
- run ID;
- execution ID;
- report title;
- report description;
- primary content kind;
- primary content identity;
- contributing intelligence-node IDs;
- source-evidence IDs;
- source-report IDs when another report is composed into the result;
- actual report content;
- composition metadata;
- composition hash;
- certification hash;
- publication status;
- creation/update timestamps.

The library therefore stores the **names and descriptions of the user's actual reports**, not merely the names of possible products.

## 5. Exact execution boundary

A user report must remain bound to the execution that produced its content.

The report cannot silently combine content from unrelated users, unrelated runs, or unrelated execution boundaries.

When content is recursively combined, every upstream content reference must remain traversable through the persisted IRIS graph and exact lineage boundary.

## 6. Forward and reverse traversal

### Forward

`Provider/User/Authoritative Evidence`
→ `Observed State`
→ `Canonical Financial-Life State`
→ `Relational Ontology`
→ `Intelligence`
→ `Higher-Order / Recursive Intelligence`
→ `Report Composition`
→ `User Report`
→ `User`

### Reverse

`User Report`
→ `Report Composition`
→ `Derived / Intelligence Nodes`
→ `Relational / State Nodes`
→ `Observed Evidence`
→ `Provider/User/Authoritative Source`

The exact reverse path is available only where the corresponding persisted lineage exists.

## 7. Report library semantics

The Report Library must clearly distinguish:

- **defined** — a report product definition exists;
- **active** — the user has selected the definition for publication;
- **runtime** — a governed runtime output exists;
- **user-created** — an actual user-specific report has been composed and persisted;
- **limited** — the report can be shown only with explicit evidence limitations;
- **suppressed** — publication is blocked by evidence, lineage, semantic, authorization, or certification requirements.

No status may be inferred merely from a catalog definition.

## 8. No artificial report ceiling

The number of report definitions is not the intelligence capacity of IRIS.

The number of reports a user can have is not a semantic limit on IRIS.

The number of named report families is not a semantic limit on IRIS.

IRIS may create new report compositions whenever governed content can be legitimately combined into a new useful result.

Practical limits are runtime resources, authorization, evidence availability, storage, latency, materialization budgets, and usefulness—not an artificial semantic ceiling.

## 9. No-fabrication boundary

A report is never created merely because IRIS can name it.

IRIS must not create a user report from:

- fabricated financial data;
- fake provider observations;
- invented balances;
- invented transactions;
- invented income;
- invented fees;
- invented outcomes;
- fabricated causal relationships;
- fabricated forecasts presented as observations; or
- placeholder values presented as user facts.

If evidence is absent, the report must say so or remain unpublished.

Unknown is never represented as zero.

## 10. Certification

A normal user-specific derived report requires the applicable execution and report certification gates to pass.

The report library therefore cannot turn an uncertified execution into a published financial result.

Certification is not the same thing as truth in the philosophical sense. It is the governed runtime contract proving that the declared evidence, semantic dependencies, lineage, sufficiency, and execution conditions required for publication were satisfied.

## 11. Composition is open-ended

The finite catalog of predefined report definitions is not the complete report universe.

IRIS may compose a new report from content that has never had a dedicated report definition, provided the composition is governed and its lineage is explicit.

This is the report-level manifestation of the unbounded IRIS intelligence hierarchy.

## 12. Product/library boundary

The report catalog/library is a **presentation and product inventory**.

It is not a provider-data catalog.

It does not activate Plaid products.

It does not create evidence.

It does not create intelligence merely by storing a name.

It does not constrain the underlying IRIS hierarchy.

It records what IRIS has defined and, for each user, what IRIS has actually composed and published.
